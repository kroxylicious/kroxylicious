= Assigning a dedicated ServiceAccount to proxy pods

[role="_abstract"]
By default, proxy pods use the `default` ServiceAccount of their namespace.
To give the proxy its own Kubernetes identity, for example, to use a cloud provider's workload identity integration, set `serviceAccountName` in the `infrastructure` section of your `KafkaProxy` specification.

The ServiceAccount is user-managed.
Create it in the same namespace as the `KafkaProxy`, together with any annotations, RBAC bindings, or `imagePullSecrets` it needs.
Settings on the namespace's `default` ServiceAccount, such as `imagePullSecrets`, are not inherited.
The operator only references the ServiceAccount by name; it does not create, modify, or delete it.

.Example `KafkaProxy` configuration with a dedicated ServiceAccount
[source,yaml]
----
kind: KafkaProxy
apiVersion: kroxylicious.io/v1alpha1
metadata:
  namespace: my-proxy
  name: simple
spec:
  infrastructure:
    serviceAccountName: kroxylicious-proxy
----

Changing `serviceAccountName` replaces the proxy pods through a normal Deployment rollout.
To rotate to a new ServiceAccount, create the new ServiceAccount first, update the `KafkaProxy`, and delete the old ServiceAccount only after the rollout completes.
Removing `serviceAccountName` returns the proxy pods to the namespace's `default` ServiceAccount.
Changes to the ServiceAccount itself, such as its annotations or `automountServiceAccountToken`, do not restart running pods; restart the Deployment to apply them.

If the referenced ServiceAccount does not exist, Kubernetes cannot create the replacement pods and does not fall back to `default`.
The Deployment reports a `ReplicaFailure` condition with reason `FailedCreate`, and the ReplicaSet events name the missing ServiceAccount.
The rollout completes once the ServiceAccount is created or the `KafkaProxy` references an existing one.

The proxy does not need Kubernetes API access for normal operation.
Grant the ServiceAccount only the permissions that your identity integration requires, and consider setting `automountServiceAccountToken: false` on it unless that integration needs a token.
Anyone who can modify a `KafkaProxy` can choose which ServiceAccount its pods use, so restrict write access to `KafkaProxy` resources accordingly.
