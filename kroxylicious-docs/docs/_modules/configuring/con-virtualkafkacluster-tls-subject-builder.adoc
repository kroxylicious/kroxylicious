= Configuring the TLS subject builder for client-to-proxy connections

[role="_abstract"]
When a Kafka client authenticates to the proxy using a TLS client certificate, the proxy can build an authenticated subject from the certificate.
A subject contains one or more principals, such as a user name, and which principals are created depends on the subject builder configuration.
The `tlsSubjectBuilder` field on a `VirtualKafkaCluster` configures how the proxy builds this subject.
If `tlsSubjectBuilder` is not specified, the proxy does not build any principals from the client certificate.
The client remains anonymous unless it then authenticates using SASL, for example through a SASL Inspection or SASL Termination filter.

NOTE: SASL subject builders are configured on the relevant SASL filter, not here.
If both TLS client authentication and SASL authentication are in use, a successful SASL login replaces the TLS certificate-based subject.
A failed SASL login results in the client being anonymous, regardless of its certificate.

For information about the available subject builder plugins and their rule syntax, see the _Configuring the transport subject builder_ section of the Kroxylicious proxy documentation.

NOTE: The built-in `DefaultTransportSubjectBuilderService` requires `configTemplate` to be present.
Custom subject builder plugins may not require it.

.Example `VirtualKafkaCluster` using `DefaultTransportSubjectBuilderService` to map a client TLS certificate CN to a user principal
[source,yaml]
----
kind: VirtualKafkaCluster
metadata:
  # ...
spec:
  # ...
  tlsSubjectBuilder:
    type: DefaultTransportSubjectBuilderService
    configTemplate:
      addPrincipals:
        - from: clientTlsSubject
          map:
            - replaceMatch: "/(?:.*,)?CN=([^,]+)(?:,.*)?/$1/"
            - else: anonymous
          principalFactory: io.kroxylicious.proxy.authentication.UserFactory
----

where:

* `type` is the Java class name of the subject builder plugin implementation. This field is required when `tlsSubjectBuilder` is present.
* `configTemplate` contains the subject builder's configuration.
  For `DefaultTransportSubjectBuilderService`, this is the set of rules described below.

The `replaceMatch` rule `/(?:.*,)?CN=([^,]+)(?:,.*)?/$1/` extracts the `CN` component of the certificate subject distinguished name (DN) wherever it appears in the RFC 2253 string and uses it as the username.
For example, a certificate with DN `CN=myapp,O=example` produces user `User:myapp`.
The `else: anonymous` clause means that if no rule matches, the client is treated as anonymous.

[TIP]
====
To see the subject string that the proxy matches against, run the following command:

[source,bash]
----
openssl x509 -in <cert-file> -noout -subject -nameopt RFC2253
----

The output is in RFC 2253 format, for example `CN=myapp,O=example`.
Commas that are part of an attribute value appear escaped as `\,` rather than as a field separator.
====

When `configTemplate` references a `Secret` or `ConfigMap` that does not exist, the operator sets the `ResolvedRefs` condition on the `VirtualKafkaCluster` to `False` and the proxy excludes the virtual cluster from its configuration until the referenced resources exist.

When the referenced resources exist but their contents change, the operator rolls the proxy pods to pick up the updated configuration.
