= Choosing a SASL mechanism

[role="_abstract"]
When configuring SASL authentication, the choice of mechanism affects the security properties, infrastructure requirements, and operational characteristics of your deployment.
This section compares the PLAIN, SCRAM, and OAUTHBEARER mechanisms across several security and operational dimensions to help you make an informed choice.

The choice of SASL mechanism is independent of the choice of xref:con-choosing-authentication-approach-{context}[authentication approach] (Passthrough, Inspection, Termination, or OAuthBearer Validation).
However, some authentication approaches constrain the available mechanisms.
For example, SASL Termination currently supports only the `OAUTHBEARER` mechanism.

This section uses _server_ to refer to whichever component performs SASL authentication — either the Kafka broker or the Kroxylicious proxy, depending on your authentication approach.
Where a point applies specifically to Apache Kafka brokers or to the proxy, the more specific term is used.

== Mechanism overview

PLAIN::
The client sends a username and password in plain text within the SASL exchange.
The security of the credentials depends entirely on the TLS layer protecting the connection.
PLAIN is defined in https://tools.ietf.org/html/rfc4616[RFC 4616].

SCRAM-SHA-256 and SCRAM-SHA-512::
The Salted Challenge Response Authentication Mechanism (SCRAM) authenticates the client using a challenge-response protocol.
The client proves knowledge of the password without transmitting it.
SCRAM is defined in https://datatracker.ietf.org/doc/html/rfc5802[RFC 5802], with the SHA-256 variant specified in https://datatracker.ietf.org/doc/html/rfc7677[RFC 7677].

OAUTHBEARER::
The client presents an OAuth 2.0 bearer token (typically a JWT) obtained from an authorization server.
Bearer tokens are typically short-lived, limiting the window of exploitation if a token is intercepted.
The server validates the token using public keys retrieved from a JWKS endpoint, without requiring the client to send a password.
OAUTHBEARER is defined in https://datatracker.ietf.org/doc/html/rfc7628[RFC 7628].

== Security considerations

=== Protection against TLS termination and middlebox compromise

*Threat:* An attacker controls or has access to a TLS-terminating component such as a reverse proxy, API gateway, load balancer, or network monitoring appliance.

PLAIN:: The plain-text password is visible to any component that terminates TLS before the authentication server.
An attacker with access to such a component can capture credentials directly.

SCRAM:: The password is never transmitted, even within the TLS session.
The SASL exchange contains only nonces and HMAC proofs, so an attacker with access to a TLS-terminating middlebox cannot extract the password from the SASL messages.

OAUTHBEARER:: The bearer token is transmitted within the TLS session, similar to PLAIN.
However, bearer tokens are typically short-lived, which limits the window during which a captured token can be replayed.
The user's underlying credentials (such as a username and password used to obtain the token from the authorization server) are not exposed.

=== Protection against rogue servers and man-in-the-middle attacks

*Threat:* An attacker impersonates the server or interposes between the client and server, for example, by using a compromised internal CA or a malicious proxy certificate.

PLAIN:: No protection at the SASL layer.
The client sends the password to whatever server terminates TLS.
Correctly configured TLS (with proper certificate validation and trusted CAs) is an adequate mitigation of this risk, because TLS itself verifies the identity of the server before any credentials are sent.

SCRAM (without channel binding)::
SCRAM provides _mutual authentication_: the server must prove possession of the user's `ServerKey` before authentication completes.
This prevents a rogue server that does not possess the correct `ServerKey` from completing the SCRAM handshake.
+
The SCRAM standard defines channel binding variants (such as `SCRAM-SHA-256-PLUS`) that can detect a TLS-terminating man-in-the-middle.
However, *Apache Kafka does not support SCRAM channel binding variants*.
Without channel binding, a man-in-the-middle that proxies the full SCRAM exchange between the genuine client and genuine server is not detected.

OAUTHBEARER:: The token is sent to whatever server terminates TLS.
The token does not reveal the user's underlying credentials, and the short lifetime of an individual token limits the impact of a single interception.
However, if the rogue server remains undetected, it can capture successive tokens over time and maintain ongoing access.

=== Cross-service token replay

*Threat:* An attacker obtains a valid bearer token (for example, from application logs, a compromised service, or a TLS-terminating middlebox) and presents it to a different service to gain unauthorized access.

PLAIN:: Not applicable.
Passwords are not scoped to a particular service, so a stolen password grants access to any service where the same credentials are accepted.

SCRAM:: Not applicable.
SCRAM credentials are service-specific by design: the derived keys are computed with a salt chosen by the server, so credentials stolen from one service cannot be replayed against another.

OAUTHBEARER:: Bearer tokens can include an `aud` (audience) claim that identifies the intended recipient.
If the server is configured to validate the audience, it rejects tokens that were issued for a different service.
+
To protect against cross-service replay, configure a unique audience value for your Kafka deployment and ensure that both the authorization server and the server enforce it.
Tokens issued without an audience claim, or with an overly broad audience, can be replayed against any service that accepts them.

=== Protection against credential database theft

*Threat:* An attacker gains access to the authentication credential store on the server.

PLAIN:: The server must be able to verify the plain-text password.
In principle, a server could store passwords using a strong hashing algorithm, but Apache Kafka currently stores PLAIN credentials as a plain-text username/password mapping in the broker configuration.
An attacker who gains access to the broker configuration obtains all passwords directly.

SCRAM:: The server stores derived keys (`StoredKey` and `ServerKey`) computed using PBKDF2.
An attacker who obtains these derived keys cannot directly authenticate as the client — `StoredKey` is a one-way hash of `ClientKey`, so producing a valid authentication proof requires an offline attack to reverse the hash.
The attacker can, however, impersonate the _server_ using `ServerKey`.
Crucially, the original password cannot be recovered from the stored keys, which prevents credential-stuffing attacks against other services where the user may have reused the same password.

OAUTHBEARER:: The server does not store user passwords.
It stores only the public keys (via JWKS) used to verify token signatures.
Theft of the JWKS public keys does not allow an attacker to generate valid tokens or recover user credentials.
The credential store is maintained by the authorization server, not the server.

=== Resistance to password recovery from stolen credentials

*Threat:* An attacker who has stolen the credential store attempts to recover user passwords, either directly or through offline brute-force and dictionary attacks.

PLAIN:: *None.*
Apache Kafka currently stores PLAIN credentials in plain text, so an attacker who obtains the credential store has immediate access to all passwords with no cracking required.

SCRAM:: *Moderate.*
The SCRAM protocol (https://datatracker.ietf.org/doc/html/rfc5802[RFC 5802] / https://datatracker.ietf.org/doc/html/rfc7677[RFC 7677]) mandates PBKDF2 for key derivation, so an attacker must perform an offline brute-force or dictionary attack to recover passwords.
However, PBKDF2 lacks memory hardness, which makes GPU-based cracking significantly faster compared to memory-hard algorithms such as Argon2id or bcrypt.
The PBKDF2 iteration count can be increased to raise the cost of cracking, but this also increases the cost of legitimate authentication.

OAUTHBEARER:: *Not applicable.*
The server does not store passwords; it stores only the public keys used to verify token signatures.
Resistance to password recovery depends entirely on the authorization server's credential storage practices.

== Operational considerations

=== External identity provider compatibility

PLAIN:: Because the server receives the raw password, it can forward the password to any external authentication backend such as LDAP, Active Directory, or PAM.
This makes PLAIN the most flexible mechanism for integration with legacy or third-party identity infrastructure.

SCRAM:: SCRAM requires the server to store SCRAM-specific derived keys (`StoredKey`, `ServerKey`, salt, and iteration count).
External identity directories such as LDAP or Active Directory do not natively store SCRAM derivation keys, making integration with these backends difficult.

OAUTHBEARER:: Designed for integration with external identity providers.
The authorization server handles user authentication and can integrate with LDAP, Active Directory, social identity providers, multi-factor authentication, and other enterprise identity infrastructure.
The server only needs to validate the resulting tokens.

=== Authentication latency

Kafka uses long-lived connections, with authentication at connection establishment and occasional reauthentication.
The additional latency from extra authentication round trips is small in this context and is not normally a paramount concern.

PLAIN:: Requires one round trip: the client sends credentials, and the server responds with success or failure.

SCRAM:: Requires two round trips for the challenge-response exchange (`client-first` -> `server-first` -> `client-final` -> `server-final`).
Over high-latency network links, this doubles the authentication negotiation time compared to PLAIN.

OAUTHBEARER:: Requires one round trip between the client and server.
However, the client must first obtain a token from the authorization server, which adds latency before the Kafka connection is established.
Token caching and refresh strategies can spread this cost across multiple connections.

=== Infrastructure requirements

PLAIN:: No additional infrastructure beyond the server (or whatever backend the server delegates authentication to).

SCRAM:: No additional infrastructure beyond the server.
Credential management (creating and updating SCRAM credentials) is handled through Kafka's built-in tooling.

OAUTHBEARER:: Requires an OAuth 2.0 authorization server and a JWKS endpoint for token validation.
The availability of authentication depends on these services being reachable.

=== Reauthentication and credential rotation

Kafka supports reauthentication on long-lived connections (https://cwiki.apache.org/confluence/display/KAFKA/KIP-368%3A+Allow+SASL+Connections+to+Periodically+Re-Authenticate[KIP-368]).
When reauthentication is enabled, the broker tells the client when its session expires, and the client initiates a fresh SASL handshake on the existing connection before the session lifetime elapses.

OAUTHBEARER:: The session lifetime is derived from the token's expiry time.
When reauthentication occurs, the client obtains a fresh token from the authorization server, so reauthentication also rotates the credential.
If an earlier token was compromised, the new handshake uses a different token, limiting the window of exposure.

SCRAM:: The Kafka SCRAM implementation does not set a credential lifetime.
Reauthentication occurs only if the broker's `connections.max.reauth.ms` is configured, and the client re-sends the same password-derived proof.
Because the underlying password does not change during reauthentication, credential rotation does not occur.
An exception is SCRAM authentication using delegation tokens: the delegation token's expiry time is used as the credential lifetime, and reauthentication behaves similarly to OAUTHBEARER.

PLAIN:: Like SCRAM, no credential lifetime is set.
Reauthentication is driven solely by `connections.max.reauth.ms`, and the client re-sends the same username and password.
No credential rotation occurs.


=== Implementation and parser complexity

PLAIN:: Trivially parsed (`\0username\0password`), minimizing the parser bug surface area.

SCRAM:: Requires cryptographic hashing, HMACs, nonce tracking, and a multi-step state machine.
The SCRAM standard mandates SASLprep normalization of usernames and passwords, but Apache Kafka does not currently implement SASLprep.
Incorrect implementations can introduce timing attacks or normalization bypasses.

OAUTHBEARER:: Requires JWT parsing, signature verification against JWKS, and validation of standard claims (expiry, audience, issuer).
Client libraries must handle token acquisition and refresh.

== When to use each mechanism

Use PLAIN when::
* You need to integrate with an external identity provider such as LDAP, Active Directory, or PAM, because the server receives the raw password and can forward it to any authentication backend.
* You want the simplest possible SASL configuration with minimal client and server complexity.
* You accept that credentials are only protected by the TLS layer and that credential rotation requires out-of-band password changes.

Use SCRAM when::
* You want to protect credentials against TLS-terminating middleboxes or compromised TLS endpoints, because the password is never transmitted.
* You do not need to integrate with external identity providers that lack SCRAM-specific credential storage.
* You want protection against credential database theft, where the stored derived keys cannot be directly used to impersonate a client.

Use OAUTHBEARER when::
* You have (or are willing to deploy) an OAuth 2.0 authorization server and JWKS endpoint.
* You want automatic credential rotation through short-lived tokens, so that compromised credentials expire without manual intervention.
* You need to integrate with enterprise identity infrastructure such as OpenID Connect, multi-factor authentication, or federated identity.
* You want reauthentication to rotate the credential, not just re-verify the same one.
