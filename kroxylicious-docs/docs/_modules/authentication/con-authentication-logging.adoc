= Authentication logging

[role="_abstract"]
The proxy emits structured log messages for authentication events.
These log messages provide visibility into authentication activity and can serve as a basic form of audit trail until a dedicated audit log is available.

== Runtime authentication logs

The proxy runtime logs authentication outcomes announced by filters at `INFO` level.
These messages are emitted by the `FilterHandler` class regardless of which filter triggers the authentication event.

Authentication success::
Logged at `INFO` level with the following structured fields:
+
* `mechanism` — the SASL mechanism used (for example, `SCRAM-SHA-256`)
* `subject` — the authenticated subject constructed by the subject builder
+
Message: `Filter announces client has passed SASL authentication`

Authentication failure::
Logged at `INFO` level with the following structured fields:
+
* `mechanism` — the SASL mechanism used, or `null` if not yet determined
* `authorizedId` — the authorization ID of the client, or `null` if not available
* `error` — the error message from the authentication failure
+
Message: `Filter announces client has failed SASL authentication`
+
The full stack trace is included only when the log level is set to `DEBUG`.
At `INFO` level, the log message includes a hint to increase the log level for the stack trace.

== SASL Inspection filter logs

The `SaslInspection` filter emits additional log messages specific to the SASL inspection process.

.SASL Inspection filter log messages
|===
|Level |Message |Structured fields |When emitted

|INFO
|`Client attempted request without having SASL authentication`
|`sessionId`, `apiKey`, `authenticationDisposition`, `outcome`
|A client sends a Kafka request without having completed SASL authentication, and `requireAuthentication` is enabled.

|INFO
|`Client sent authorization request containing a SASL response that could not be interpreted`
|`clientId`, `sessionId`, `error`
|The proxy could not parse the SASL response from the client.
The full stack trace is included only at `DEBUG` level.

|INFO
|`Authentication failed`
|`sessionId`
|The broker rejected the client's SASL credentials.

|INFO
|`Server rejects SASL credentials`
|`errorCode`, `sessionId`
|The broker returned an error code in response to the SASL authentication attempt.

|INFO
|`Server has accepted an expired SASL credentials. Client must re-authenticate`
|`sessionId`
|The broker accepted credentials that are nearing expiry, and the client will need to re-authenticate.

|WARN
|`Exception caught while trying to build subject`
|`error`
|The subject builder threw an exception while constructing the authenticated subject.
The full stack trace is included only at `DEBUG` level.
|===

== OAuthBearer Validation filter logs

The `OauthBearerValidation` filter emits log messages at `DEBUG` level for authentication events.

.OAuthBearer Validation filter log messages
|===
|Level |Message |Structured fields |When emitted

|DEBUG
|`SASL Authentication failed`
|`error`
|JWT token validation failed (for example, expired token, invalid signature, or audience mismatch).
The full stack trace is always included.

|DEBUG
|`SASL error`
|`error`
|An unexpected error occurred during the SASL handshake.
The full stack trace is always included.
|===

== Operational guidance

Use the `sessionId` field to correlate authentication events with other log messages for the same client connection.
This is particularly useful when diagnosing authentication failures in environments with many concurrent connections.

To see full stack traces for authentication failures:

* For the SASL Inspection filter, set the log level for `io.kroxylicious.filter.sasl.inspection` to `DEBUG`.
* For the OAuthBearer Validation filter, the filter already logs at `DEBUG` level, so set the log level for `io.kroxylicious.filter.oauthbearer` to `DEBUG`.
* For runtime authentication announcements, set the log level for `io.kroxylicious.proxy.internal` to `DEBUG`.

For information on configuring log levels, see the monitoring section of the {ProxyGuide}.
